# Reflection

## Development process and key architectural decisions

I built this with Claude Code, working from a plan we agreed on before writing any code, then iterating hard on it once real data and real testing were in the loop.

**The first and biggest decision was how to ground answers in the data at all.** Census questions aren't really "find the relevant document" questions — "what's the population of Travis County" needs an exact sum across a few hundred rows, not a similarity match against a chunk of text. That ruled out RAG immediately: RAG is the right tool when the answer is *somewhere in a passage*, and wrong when the answer is a *computation over rows*. So the only real options were (a) let the model write real SQL against Snowflake and execute it, or (b) use Cortex Analyst, Snowflake's own managed text-to-SQL feature. Cortex Analyst was genuinely tempting — it's the "intended" answer for exactly this problem. I didn't use it for two concrete reasons: it's region-gated on trial accounts, which is a real risk of losing hours to an account migration with a 24-hour clock running, and it's a managed black box — using it would hide most of the actual engineering (prompt design, tool-use loop, guardrails, error handling) that the assignment says it's scoring. So I built the tool-use loop by hand and used Snowflake purely as the warehouse.

**Given that, the next question was how much of the schema to hand the model.** The dataset turned out to have around 365 distinct concepts (a "concept" being one specific measurement, like "Total Population" or "Sex By Age" — see the README for the full table/concept/column breakdown), some of them bundled into physical tables with 400+ columns. Hardcoding all of that into the prompt was never realistic — it'd be enormous, slow to reason over, and the model would still have to search through it. My intuition here was the same one you'd use onboarding a new analyst: you don't hand them the entire data dictionary on day one, you tell them the dozen tables they'll use constantly, and you make sure they know *how* to look up anything else themselves. So `agent/schema_context.py` hand-documents about a dozen common concepts directly, and everything else goes through a lookup mechanism — which itself went through two complete rewrites, described below, because my first two attempts at that mechanism didn't actually hold up under real testing.

**Snowflake authentication turned into its own small saga.** The obvious approach — a service account with a password — failed the moment I tried it programmatically: new Snowflake trial accounts enforce MFA on password logins, and MFA has no way to complete itself for a non-interactive client. That's not just an inconvenience for local testing, either — it would have broken the *deployed* app too, since Streamlit Cloud is exactly the kind of non-interactive client that can't click through an MFA prompt. So the real fix had to work for an automated service account, not just for me sitting at a terminal — which pointed straight at key-pair authentication, which Snowflake explicitly designed for service accounts and which isn't subject to the MFA policy at all.

**Guardrails are two independent layers, on purpose.** The intuition is basic defense-in-depth: a single point of failure means a single mistake takes down the whole protection. So there's a fast, cheap classifier that screens messages before the real agent ever runs (catches obviously off-topic or unsafe input cheaply, and — just as importantly — proves the expensive Snowflake/Claude path never even executes for those messages), and separately, the main agent's own system-prompt instructions repeat the same refusal behavior as a backup. If the classifier ever misclassifies something, the second layer is still there.

## The retrieval system: two failed attempts before the one that worked

This is worth walking through in detail because it's the part of the build that actually taught me something, rather than just executing a plan.

**Step 1 — the naive version.** My first approach for "concepts outside the curated dozen" was to let the model write its own SQL against the metadata table directly — a plain `WHERE TABLE_TITLE ILIKE '%...%'` search. It's simple, needs zero extra infrastructure, and it worked in early testing (a "how many veterans" question resolved correctly). That success was misleading, though — it worked because the concept name happened to be distinctive enough that a crude substring search couldn't miss it.

**Step 2 — testing found it break.** Two harder questions exposed the real problem. Asked for "travel time," the model's search genuinely matched the right table, but a row-limit cap on the unranked results let a different, larger table crowd it out entirely — re-running the same search with no limit confirmed the right answer was there all along, just never seen. Asked "how many males under 5," the model had no way to know *which* of ten internal column-numbering levels held that specific detail, guessed wrong twice, and burned its entire round budget without ever answering. Neither of these is a hypothetical edge case — they're exactly the kind of ordinary question a real user would ask.

**Step 3 — first fix, which also failed.** My instinct was to replace the crude `ILIKE` search with a real hybrid retrieval setup: TF-IDF for keyword matching, sentence-transformer embeddings for semantic matching, combined with Reciprocal Rank Fusion (merging by rank position rather than raw score, since the two methods' scores live on different scales that can't be compared directly). This is the textbook right way to build search over a few thousand short documents. I built it, then actually tested it rather than assuming it worked — and it still failed the exact same "travel time" case. The reason took some digging: I was still ranking at the level of individual *columns*, and a concept with 98 columns (like "Sex By Age") gets 98 separate entries competing for a fixed-size results list, while a concept with 2 columns only gets 2 — an unfair structural bias that has nothing to do with actual relevance. The correct table's columns were individually reasonable matches; there just weren't enough of them to survive being outnumbered.

**Step 4 — the fix that actually worked.** The intuition, once I saw the real cause, was to stop conflating two different questions: "which broad concept is relevant" and "which specific column within it." I split retrieval into two stages. Stage one ranks *concepts*, not columns — one document per concept (about 365 of them), so every concept gets exactly one shot at the ranking regardless of how many columns it happens to contain. Stage two doesn't need to rank anything at all: once a concept is chosen, it's a small, complete, deterministic list of every column that concept has, and the model just reads it and picks the one that matches. This removes the column-count bias structurally instead of trying to tune around it, and it also solves the second bug for free — there's no field-level number to guess anymore, just a list to read. Both previously-broken questions now answer correctly and consistently; I checked each three times against the real stack before trusting it.

The honest lesson from this whole detour: my first fix *felt* right (hybrid search is the standard, well-regarded approach) and still failed, because I fixed the search algorithm without questioning the granularity it was operating on. Testing the fix, not just building it, is what caught that.

## What I'd improve or do differently with more time

- **Run the eval suite multiple times, not once.** Two of the bugs I found this session — a guardrail inconsistency and a round-budget off-by-one — were intermittent, only visible because I happened to re-run something a second time. A single pass/fail per case almost certainly hides others I haven't caught yet.
- **Broader coverage of the long-tail retrieval system.** I've directly verified it on maybe five concepts (veterans, commute time, sex-by-age breakdowns) out of ~365. That's a reasonable spot check of the mechanism, not real coverage of the space.
- **Real token streaming**, instead of a spinner followed by the answer appearing all at once — would feel noticeably more responsive on longer, multi-query answers.
- **Adversarial/red-team testing.** I tried one prompt-injection phrasing and it was blocked; a person deliberately trying several bypass strategies hasn't been simulated.
- **Connection pooling.** The app caches one Snowflake connection per browser session, which is fine for the traffic a demo will see but wouldn't hold up under real concurrent load.
- **Conversation length management.** History just grows, capped at a hard 40 messages. A real deployment would want to summarize or trim older turns before that becomes a problem.
- **Basic observability** — no logging of questions, generated SQL, or latency per turn right now. For an actual handoff to a team, that's the first thing I'd add so a bad answer could be debugged after the fact instead of only being reproducible by accident.

## Edge cases and failure modes identified but not fully addressed

- **Prompt injection through tool results, not just user messages.** Data coming back from Snowflake is fed to the model as a tool result; if the dataset itself ever contained adversarial text, it would reach the model unfiltered. Low real risk since the Marketplace data isn't user-writable, but worth naming — the guardrails only inspect what the user typed, never what comes back from the database.
- **Mixing data vintages within one answer.** The dataset spans 2019 and 2020 ACS estimates plus a separate 2020 Redistricting table built on an entirely different methodology (actual counts, not survey estimates). The model is told to state which year it used, but nothing structurally prevents it from silently combining a 2019 figure with a 2020 one across two calls in the same answer.
- **No stemming in the retrieval system.** A plain plural/singular mismatch — searching "males" against corpus text that says "Male" — can weaken the keyword half of the search. It didn't cause a failure in testing, because concept-level search rarely hinges on getting one specific word form exactly right, but it's a real, known gap rather than something I've actually closed.
- **Non-English or malformed input** was never explicitly tested — empty strings, extremely long input, non-UTF8 text.
- **No load testing at all**, on an app that's now genuinely public and unauthenticated.

## How I approached testing, and what I'd add

I ended up with four layers, and the reason there are four rather than one or two is that each one catches a category of problem the others structurally cannot.

**Unit tests** check the pure logic in isolation — does the SQL safety validator actually reject `DROP TABLE`, does the guardrail classifier fail open (rather than locking users out) if the classification call itself errors. No AI, no database, nothing non-deterministic; if one of these breaks, it's unambiguously a bug in my own code.

**Control-flow tests** simulate the model with a scripted fake, so I can check that the tool-use loop itself — retries, error handling, giving up gracefully after too many rounds — behaves correctly without needing a real (slow, non-deterministic, costly) API call for every scenario.

Neither of those layers can tell you whether the *real* model, asked a *real* question, actually writes correct SQL and gives a good answer — a fake AI can't prove anything about real AI behavior. That's what the **manual smoke test** is for: real questions against the real Claude and real Snowflake. This is genuinely how the first bugs in this project were found — case-sensitive column names that fail silently unless quoted, an empty-answer bug caused by the model's internal reasoning eating its whole token budget, the MFA wall described above. None of those could have shown up in the first two layers, because they only exist in the gap between "what I assumed the real system would do" and what it actually does.

The gap in the smoke test is that a human has to read the transcript and judge it — not repeatable as a pass/fail gate, and not something I can realistically re-run after every small change. That's what pushed me to build the **eval system**: the same kind of real questions, but each one now carries automated checks — does the answer contain a number close to a value I've independently verified, was the database actually queried (or correctly *not* queried, for a message that should've been rejected), did the guardrail classify it as expected, did it respond in time. A small advisory layer uses a second, cheap model call to judge the handful of things a keyword check genuinely can't capture, but that layer is explicitly not authoritative — an AI grading an AI isn't ground truth, so it's reported separately and never counted toward the real pass/fail total.

That system paid for itself. Across the session it — combined with some direct live tracing when something looked off — found six real bugs total: the guardrail inconsistency and round-budget issue mentioned above, a batch of tool calls getting thrown away entirely because one of them got cut off mid-generation, silent truncation on a broad query that could have produced a confidently wrong total, and the two retrieval failures that led to the whole two-stage rewrite. Every one of them now has a permanent regression test, so the same bug can't silently come back.

What I'd add next: running each eval case several times automatically to get a real pass *rate* rather than trusting a single green run, given that I already know some of these failures are intermittent; a much wider sample of long-tail concepts instead of the handful I've hand-checked; deliberate adversarial cases; and running the eval suite directly against the deployed app rather than a local connection, since I don't actually have proof the two environments behave identically.
